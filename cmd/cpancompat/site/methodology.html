Methodology and reproduction

What the numbers on this site count, how each distribution is built and tested, how its outcome and the cause of a failure are decided, and how to make a survey yourself. Everything here is done by the cpancompat command of this repository; its source is the reference.

The reference set

A survey starts from a snapshot of CPAN: the package index (02packages.details.txt.gz, the index CPAN clients resolve modules against) and the metadata of every release MetaCPAN marks latest, one release per distribution: {{num $s.Snapshot.Distributions}} distributions in the snapshot of {{day $s.Snapshot.FetchedAt}}. Each declared requirement is resolved to the distribution that provides the module, which gives the dependency graph: what each distribution needs to be configured, built, tested and run, and how many distributions need it, directly or indirectly (its dependents).

Not every distribution on CPAN works on a given perl, or on Linux, or at all. The survey measures against the distributions that are known to work on the perl version the interpreter is built from: the reference set is the latest releases whose CPAN Testers reports on perl {{$s.Snapshot.Perl}}, made on Linux, pass more often than they fail. That is {{num $s.Snapshot.ReferenceDistributions}} distributions. A release nobody has tested on that perl is outside the set; it is still built and tested when a distribution of the set needs it.

Building and testing a distribution

Every distribution of the set is run with everything it needs, in dependency order, the most depended upon first. Its requirements are installed by the same interpreter, the same way, not taken from elsewhere. Each distribution gets a container of its own, made from one image:

  • Debian (bookworm) with a C toolchain, the tools build scripts run and the development files of the C libraries CPAN distributions bind to, the same for both interpreters. In the image for go-perl the perl command is gperl; the image for perl itself is the same environment built on the official perl image.
  • The distribution runs as an unprivileged user in a login environment, as CPAN clients and smokers do, with no capabilities (--cap-drop ALL, no-new-privileges), a limit on processes, memory and CPUs, the archives mounted read-only and no writable directory of the machine that runs it. Its records are copied out of the container as plain files and directories only. CPAN code is untrusted: the harness is built to contain it.
  • Network: {{with $sub.Meta.Network}}{{.}}{{end}}
  • The environment CPAN clients set: PERL_MM_USE_DEFAULT=1, NONINTERACTIVE_TESTING=1, PERL_USE_UNSAFE_INC=1, and a virtual X display for the tests.

A distribution whose requirements are not all met is still built and tested, as CPAN.pm does. When it fails while a requirement it computed is unmet, it waits for the distribution that provides the requirement and runs again once that one has finished (up to four attempts). A distribution is installed whenever it builds, whatever its tests say, so that the distributions that need it can be tried.

blocked and prerequisites_unmet put a failure down to what the distribution lacked: it did not pass, and a distribution providing a module it lacked did not install (blocked), or a requirement it computed cannot be met at all, such as a newer perl or a module no distribution provides (prerequisites_unmet). It was run anyway, and its page shows how that went.

Causes

Why a distribution that did not pass failed is read from its records and the log of its failing phase. The logs are other programs' output (make, the C compiler, perl, the test harness, the distribution's own scripts), so this is done by the patterns of their messages:

  1. The evidence lines are taken from the log: for failing test files, the lines the harness printed for each of them; otherwise the lines that report an error (compiler and linker errors, Can't locate, panic, failed tests, …); without any, the last lines.
  2. The first cause, in the order of the table, whose messages appear in the evidence is the cause.
  3. A phase that ran out of time is classified by what its processes were doing 15 seconds before the limit: waiting without using the CPU (blocked), one program on the CPU for minutes (spinning), or a program that started recently on the CPU (slow: still going through its test files).
  4. Every distribution gets a cause; when nothing above applies, it is not analysed.

The comparison

A distribution of the set can still fail in this environment on perl itself: a test that needs a service, a desktop or a file that is not there, a release that is broken in a way the CPAN Testers reports do not show. So the same distributions are run on perl {{$s.Snapshot.Perl}} itself, in the same images and harness, and each distribution falls into one of four buckets: both pass, only go-perl fails, both fail, only perl fails. A distribution a run has no record of counts as not passing there. What only go-perl fails is what go-perl has to fix; what both fail is down to the environment or the distribution.

A blocked distribution names the distributions that blocked it; following those through the ones that are blocked themselves ends at distributions that were run and did not install. Those are listed by how many of the distributions only go-perl fails they block.

Reproducing a survey

Surveys run on a machine of your own; the results in the repository are what this site is generated from. The repository's README has the details; in short:

  1. Docker with 8 CPUs, 16 GB of memory and 60 GB of disk, in a virtual machine of its own (such as a colima profile): the harness installs firewall rules in the Docker host, and CPAN code is untrusted.
  2. A gperl binary for Linux on the architecture of the containers, built from go-perl.
  3. make survey GPERL=path/to/gperl GPERL_COMMIT=… fetches the snapshot and the CPAN Testers reports, builds the dependency graph and both images, runs both interpreters on the reference set (several hours each), and writes the results and this site.
